# Vanilla JS 기반 개발자 블로그
Vanilla JS만을 사용하여 상태 관리, 렌더링 흐름, URL 동기화 등 React의 핵심 동작 원리를 이해하는 데 목적을 둔 블로그 애플리케이션입니다.

## 1. 프로젝트 개요

### 1.1. Vanilla JS로 구현한 React 핵심 개념
- **중앙 집중형 상태 관리:**<br/>
  페이지 전반에서 사용되는 상태를 단일 `state` 객체로 관리하여 상태 변경의 출처를 명확히 하고 데이터 일관성을 유지하도록 설계했습니다.

- **선언형 컴포넌트 설계:**<br/>
  UI를 `createPostTemplate`, `createPageTemplate`와 같은 독립적인 함수로 분리하고, 입력된 데이터에 따라 결과만 반환하는 순수 함수 형태로 구성하여 UI를 명령형 DOM 조작이 아닌 선언형 방식으로 표현했습니다.

- **상태 변화 기반 렌더링:**<br/>
  직접적으로 DOM을 조작하는 행위를 지양하고, 상태 변경 시 `renderPosts()` 함수를 재호출하는 구조로 설계하여 데이터와 화면이 항상 일관된 상태를 유지하도록 구현했습니다.

- **URL 동기화:**<br/>
  `History API`와 `URLSearchParams`를 활용해 페이지, 정렬, 검색 상태를 URL과 동기화하는 상태 기반 라우팅 구조를 구현했습니다.

### 1.2. React 이관을 염두에 둔 이유
React를 처음 학습했을 당시, 프레임워크가 제공하는 추상화의 필요성을 명확히 이해하지 못했습니다. 이에 따라 Vanilla JavaScript 환경에서 동일한 구조를 직접 구현해 보며 React가 해결하고자 하는 문제와 그 장점을 체감하기 위해 본 프로젝트를 진행했습니다.

<br />

## 2. 기술 스택

- **HTML5** <br /> 
시맨틱 태그를 적극적으로 사용하여 문서 구조의 의미를 명확히 하고,
스크린 리더 기준에서도 논리적인 DOM 흐름을 유지하도록 설계했습니다. 이를 통해 웹 접근성과 SEO의 기본 전제를 충족하는 구조를 의도했습니다.

- **CSS3** <br /> 
FlexBox 중심으로 레이아웃을 구성하여 뷰포트 변화에 유연하게 대응하도록 구현했습니다. 또한 CSS 변수를 도입해 라이트/다크 테마를 상태 기반으로 제어할 수 있도록 설계했습니다.

- **JavaScript (ES6+)** <br />
프레임워크 없이 순수 JavaScript만으로 애플리케이션을 구성했습니다. 단일 `state` 객체를 기준으로 '데이터 가공 -> 렌더링' 흐름을 분리하여 React의 선언적 렌더링 모델을 Vanilla JS 환경에서 재현하는 것을 목표로 했습니다.

<br />

## 3. 핵심 기능
- **게시글 목록 렌더링** <br />
게시글 목록 데이터를 상태 기준으로 가공한 뒤, 가공된 데이터를 `map()` 메서드를 이용해 순차적으로 DOM에 렌더링했습니다.

- **게시글 필터링** <br />
조건문과 `filter()` , `includes()` 등의 배열 메서드를 활용해 태그, 검색어, 정렬 조건에 따라 게시글 데이터를 동적으로 필터링하는 기능을 구현했습니다.

- **페이지네이션** <br />
가공된 게시글 데이터, 현재 페이지, 페이지 사이즈를 `paginate()` 함수의 인자로 전달하여 게시글을 페이지 단위로 분할하는 로직을 구현했습니다.

- **사용자 지정 테마** <br />
브라우저의 `localStorage`를 활용해 사용자 지정 테마 기능을 구현했습니다. 사용자가 선택한 테마값을 상태로 관리하고, `syncThemeUI()` 함수를 통해 UI와 동기화했습니다. 또한 CSS 변수를 사용해 테마 변경 시 스타일을 일괄적으로 제어하도록 설계했습니다.

- **URL 상태 동기화** <br />
사용자로부터 발생한 이벤트 후에 URL 쿼리 파라미터를 갱신하고, URL 값을 파싱하여 상태 객체 `state`에 반영한 뒤 `renderPosts()` 함수를 호출해 화면을 재렌더링하도록 구현했습니다.

<br />

## 4. 설계 및 구현

### 4.1. 상태
**4.1.1. 구조** <br />
웹 애플리케이션 전반에서 공유되는 값을 하나의 단일 객체 `state`로 관리합니다.
```js
  let state = {
    posts: posts, // data
    activeTag: '', // filter
    activeSort: 'latest', // filter
    searchKeyword: '', // filter
    currentPage: 1, // pagination
    pageSize: 5, // pagination
    isMenuOpen: false, // UI
    theme: '', // UI
  };
```
URL 파라미터, UI 상태, 렌더링에 필요한 기준 값들을 모두 `state`에 두고, 렌더링 로직은 항상 `state`를 기준으로만 동작하도록 설계했습니다. 이를 통해 URL과 UI, 이벤트와 데이터 상태가 어긋나는 문제를 예방할 수 있습니다.

<br />

**4.1.2. 단일 객체인 이유** <br />
단일 `state` 객체를 사용하면 특정 시점의 화면 상태를 하나의 객체로 표현할 수 있습니다. <br />

URL 변경, 필터링, 페이지 이동 등 모든 로직이 같은 렌더링 흐름으로 수렴해야 했기 때문에, 여러 전역 변수 대신 하나의 상태 객체를 기준으로 `이벤트 -> state 변경 -> render` 구조를 명확히 유지하는 것이 중요했습니다. <br /> 

이는 이후 React의 단방향 데이터 흐름을 학습하기 위한 연습 목적도 포함하고 있습니다.

<br />

**4.1.3. 파생 상태** <br />
기존 상태로부터 항상 계산 가능한 값들은 `state`에 저장하지 않았습니다. <br />

필터링/검색/정렬이 적용된 게시글 목록, 현재 페이지에 표시될 게시글 배열, 전체 페이지 수 등의 값들은 `getDataProcessing(state)` , `paginate()` 와 같은 함수에서 렌더링 시점에 계산됩니다. <br/>

이를 통해 상태 중복을 방지하고, 데이터의 일관성을 유지하며, 항상 단일 출처를 유지하도록 했습니다.

<br/>

### 4.2. 데이터 흐름
**4.2.1. 상태 변경을 이벤트에서만 하는 이유** <br/>
상태 변경 로직을 이벤트 핸들러에서만 수행하도록 제한한 이유는, 상태 변경 지점을 명확히 통제하기 위함입니다. <br/>

DOM 조작 중간이나 렌더링 로직 내부에서 상태를 변경할 경우 데이터 흐름을 추적하기 어려워지고, UI와 상태가 서로 영향을 주는 순환 구조가 발생할 수 있습니다. <br/>

따라서 모든 상태 변경은 `이벤트 -> state 변경 -> render` 라는 단일 흐름을 따르도록 설계했습니다.

**4.2.2. 렌더링 함수의 역할** <br/>
`renderPosts()`는 현재 `state` 를 기준으로 화면 전체를 다시 계산하고 반영하는 역할을 담당합니다. <br/>

이벤트의 종류와 무관하게 상태가 변경되면 항상 동일한 렌더링 함수를 호출함으로써, UI 갱신 흐름을 단순화하고 예측 가능성을 높였습니다.

**4.2.3. 순수 함수** <br />
데이터를 가공하는 `getDataProcessing()` 함수 같은 경우, 원본 상태를 직접 수정하지 않고 입력값에 따라 항상 일관된 결과만을 반환하는 순수 함수로 구현했습니다. <br/>

이를 통해 상태 변경과 데이터 가공 로직을 분리하고, 렌더링 결과를 예측 가능하게 유지했습니다.

<br />

### 4.3. URL 동기화
**4.3.1. hash 기반으로 설계한 이유** <br/>
별도의 서버 설정 없이 CSR을 구현하기 위해 `hash` 를 기준으로 동기화하는 구조로 설계했습니다. <br/>

초기에는 History API 기반의 쿼리 스트링 방식도 고려했으나, 로컬 개발 환경에서 CSP 정책 충돌 이슈를 경험했고, 이를 회피하면서도 상태 복원이 가능한 방식으로 `hash` 기반 동기화를 선택했습니다.

**4.3.2. 동기화 흐름** <br/>
URL과 상태의 동기화 흐름은 `URL 파싱 -> state 저장 -> render` 순서로 동작합니다. <br/>

초기 로딩 및 URL 변경 시, URL 값을 파싱해 상태 객체에 저장하고 최종적으로 동일한 렌더링 함수를 호출하도록 설계하여 URL과 UI 간 불일치를 방지했습니다.

**4.3.3. React Router** <br/>
React로 이관한다면 앞서 겪었던 URL 파싱/동기화/상태 복원과 같은 로직은 React Router가 전담하게 됩니다. <br/>

이번 구현은 프레임워크가 내부적으로 처리하는 과정을 Vanilla JS 환경에서 직접 경험하기 위한 목적이었습니다.

<br />

### 4.4. 웹 표준과 접근성 고려
**4.4.1. 시맨틱 태그** <br/>
`header`, `aside`, `main`, `footer` 등 각 섹션을 시맨틱 태그로 작성해 의미를 부여했습니다.

**4.4.2. `<button>` vs `<a>`** <br/>
상태 변경이나 UI 동작을 유발하는 요소에는 `<button>` 을, 페이지 이동의 의미를 갖는 요소에는 `<a>` 를 사용했습니다.

**4.4.3. `<form>`** <br/>
서버는 구현하지 않았지만, 접근성을 고려해 `<form>` 태그 안에 검색 이벤트를 구현했습니다.

**4.4.4. 웹 표준** <br/>
aria 속성을 사용해 웹 접근성을 향상시켰습니다. 또한 role 속성을 이용해 태그가 정확히 어떤 역할을 하는지 알립니다.

<br />

## 5. 트러블 슈팅
**5.1. 이벤트 위임** <br/>
React의 개념을 구현하기 위해 항상 `renderPosts()` 함수로 DOM을 재생성하도록 설계했습니다. <br/> 

이 과정에서 기존 DOM 요소가 제거되고 새 요소가 생성되면서, 개별 요소에 직접 바인딩된 이벤트 핸들러가 유실되는 문제가 발생했습니다. <br/> 

이를 해결하기 위해 상위 요소에 이벤트를 등록하고, `event.target.closest()` 를 활용한 이벤트 위임 방식으로 동적 요소에 대한 이벤트 처리를 안정화했습니다.

**5.2. CSP 보안 정책 충돌** <br/>
URL 동기화 로직을 구현하는 과정에서 로컬 개발 환경과 CSP(Content Security Policy) 보안 정책이 충돌하는 이슈가 발생했습니다. <br/> 

History API 기반의 쿼리 스트링 방식 대신, CSP 영향을 받지 않는 `hash` 기반 URL 구조를 선택하고 `split()` 을 활용한 파싱 방식으로 상태 복원을 구현했습니다.

<br />

## 6. 향후 계획
**6.1. React 이관** <br/>
Vanilla JS로 직접 구현한 상태 관리, 렌더링, URL 동기화 구조를 React 환경으로 이관하여, 각 개념이 React에서 어떻게 추상화되는지 명확히 이해하는 것을 목표로 합니다.

**6.2. 컴포넌트 구조** <br/>
UI와 로직을 역할 단위로 컴포넌트화하여 책임을 명확히 분리하고 유지보수가 용이한 구조로 개선할 예정입니다.

**6.3. 확장** <br/>
React 이관 작업을 마치면 API와 DB를 활용해 로그인 / 사용자 / 게시글 기능 등을 확장할 것입니다.
